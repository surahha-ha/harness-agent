# 필드 리포트 1 — 실제 프로젝트 첫 적용

부트스트랩 문서를 **적힌 그대로** 따라가며 마찰을 잰 기록.
대상은 프론트엔드 애플리케이션 한 개(단일 저장소 · 1인 · 외부 저장소 없음 · 테스트와 E2E 있음).

> 목적은 "성공했다" 가 아니라 **"문서가 틀린 곳을 찾는 것"** 이다. 그래서 아래는 발견 위주다.

---

## 1. 결과 요약

| | |
| - | - |
| 절차 완주 | ①복사 ②상태확인 ③다섯 칸 ④재확인 ⑤판정검증 — **완주** |
| 실제 막힌 지점 | 문서와 실제가 어긋난 곳 **2건**, 문서에 없는 구멍 **1건** |
| 하네스 결함 | **1건** (거짓 활성) |
| 판별 질문의 효과 | **1건 적발** — 아래 F3 |
| 규칙 결과 | deny 2 · ask 1 로 시작. 8개 명령 판정에서 의도대로 동작 |

---

## 2. 발견

### 🔴 F1 — 거짓 활성 (하네스 결함 · 수정함)

복사 직후 `--status` 가 **`활성 — deny 0 · ask 0`** 이라고 답했다.

설정 파일이 있다는 이유로 "활성" 이라 보고했지만 **실제로는 아무것도 막지 않는 상태**다.
미설치보다 나쁘다 — **미설치는 의심이라도 하지만, 거짓 활성은 안심시킨다.**

→ 상태를 넷으로 갈랐다: `비활성(설치 안 됨)` / **`설정됨 · 규칙 없음`** / `꺼짐` / `활성`.
   순수 함수 `statusOf()` 로 분리하고 회귀 테스트 5건 추가.

### 🔴 F2 — 훅 연결 단계가 비어 있었다 (문서 구멍 · 수정함)

부트스트랩 ⑤가 "훅 연결" 이라고만 적혀 있고 **방법이 없었다.**
대상 프로젝트에는 훅을 걸 지점(`.githooks`·에이전트 설정 등)이 **하나도 없었다.**

즉 절차를 끝까지 따라가도 **가드는 손으로 부를 때만 도는 물건**으로 남는다.
`--status` 는 "활성" 이라 답하므로 **아무도 이 상태를 알아채지 못한다.**

→ §3 「훅 연결」 절 신설. 핵심 문장: **`--status` 는 설정 상태만 본다. 연결 상태는 보지 못한다.**
   연결 확인법은 "규칙에 걸리는 명령을 일부러 한 번 실행해 본다" 뿐이다.

### 🟡 F3 — 판별 질문이 실제로 결함을 잡았다 (긍정 발견)

`commands.unitTest` 의 판별 질문 **"이 명령의 종료코드만 보고 통과/실패를 판정할 수 있나?"** 에 답하다가,
프로젝트의 테스트 스크립트가 **watch 모드**라는 걸 발견했다. 그대로 썼으면 품질 사이클이
영원히 끝나지 않는 명령을 "검증" 이라고 부를 뻔했다. 실행 모드를 명시한 형태로 고쳐 채웠다.

> 슬롯 옆 판별 질문이 장식이 아니라는 첫 증거다. **"무엇을 넣나" 가 아니라 "어떻게 정하나" 를
> 물었기 때문에** 잡혔다.

### 🟡 F4 — 예시가 백엔드/저장소 편향 (수정함)

`dangerGuard` 예시가 컨테이너 볼륨·스키마 삭제 위주였는데, 대상 프로젝트에는 그런 게 **없다.**
되돌릴 수 없는 것이 이력 조작과 파일 삭제뿐이었다. 처음 채우는 사람은 예시와 자기 프로젝트가
너무 달라 **"우리는 해당 없나 보다" 로 넘어가기 쉽다.**

→ 부트스트랩 「흔한 실수」에 항목 추가. 프로젝트에 공유 저장소가 없으면 `shared` 는 `null` 이 정답이다.

### 🟡 F5 — 1인 프로젝트에서 승인 슬롯이 겉돈다 (수정함)

`approvals.*` 의 판별 질문은 "이걸 잘못하면 누가 수습하나" 인데, 1인 프로젝트에서는 답이 자기 자신이다.
문서는 **"협의한다는 절차가 아니다"** 라고만 하고 이 경우를 다루지 않았다.

→ 「흔한 실수」에 추가: 억지로 채우지 말고 "본인" 이라 적거나 `null`.
   없는 승인 절차를 적어 두면 그 슬롯 전체가 장식이 된다.

### 🔴 F6 — ⭐⭐ 명령 문자열 가드는 "가드를 만드는 작업" 을 막는다 (승격함)

작업 중 **이미 설치돼 있던 다른 명령 가드가 두 번 차단**했다. 둘 다 오탐이다 —
차단된 것은 실행하려는 명령이 아니라 **설정 파일에 적으려던 규칙 문자열**과
**판정 테스트에 넘기려던 인자**였다.

이건 우연한 불편이 아니라 **구조적 충돌**이다. 위험 명령 가드를 설정하려면 위험한 문자열을
텍스트로 다뤄야 하는데, 명령 전체를 통째로 매칭하는 가드는 그 둘을 구분하지 못한다.

→ 골격 1 의 「명령 위치에서만 판정한다」를 **한계 서술에서 절차 요구사항으로 승격**했다.
   행 첫머리나 `;` `&&` `|` `(` 뒤처럼 **명령이 시작될 수 있는 자리**에서만 본다.

### 🟢 F7 — 첫날 규칙은 불완전한 채로 정상이다 (수정 없음)

내가 쓴 강제 푸시 규칙이 **lease 를 붙인 형태를 통과**시켰다. 실제로는 그것도 원격 이력을 다시 쓴다.
첫날 규칙이 불완전하다는 실증이고, 부트스트랩이 이미 말한 대로다 —
**"두세 개면 충분하다. 가드는 사고를 겪을 때마다 규칙이 붙어 자란다."**

문서를 고치지 않는다. 이건 결함이 아니라 설계된 성장 경로다.

### 🟢 F8 — 부트스트랩 ②의 기대 문구가 틀렸다 (수정함)

"②에서 **비활성**이 나와야 정상" 이라고 적었는데, ①이 설정 복사를 포함하므로 실제로는 그렇지 않다.
절차와 기대가 서로 모순이었다. → F1 의 4상태 표로 대체.

## 3. 패널 조건부 2건은 어떻게 됐나

| 항목 | 상태 |
| - | - |
| 3-전문가(인계 체크리스트를 기계가 검증 못 함) | **재판정 불가** — 1인 프로젝트라 역할 인계가 일어나지 않았다 |
| 7-전문가(배포 채널 1개 가정) | **재판정 불가** — 두 번째 채널이 아직 없다 |

⭐ 예상대로 **실물이 조건을 만들어야 닫히는 항목**이다. 이번 적용은 그 조건을 만들지 않았다.
문서를 더 써서 닫으려 하지 않는다.

## 4. 훅 실연결 재측정 (2회차 방문)

같은 프로젝트에 돌아와 **실제로 훅을 걸고** F2 수정("설정≠연결")이 통하는지 쟀다.
에이전트 도구의 프로젝트 설정에 실행 전 훅으로 가드를 연결했다
(명령 실행 도구 매처 → `node .harness/danger-guard.mjs`, stdin 으로 도구 입력 JSON).

**재면서 알게 된 것 — 연결 확인은 한 단계가 아니라 사다리 3계층이다.**
F2 는 "①설정 ≠ ③발동" 만 말했는데, 그 사이에 ②가 있고 셋은 각각 다른 것을 본다.

| 계층 | 방법 | 보는 것 | 이번 결과 |
| - | - | - | - |
| ① 설정 | `--status` | 규칙이 읽히는가 | 활성 — deny 2 · ask 1 |
| ② 프로토콜 | 훅이 줄 입력 JSON 을 stdin 으로 파이프 | 명령줄·입출력 형식이 맞는가 | **4종 전부 의도대로** (deny 판정·ask 판정·통과 무출력·상태) |
| ③ 발동 | 실세션에서 규칙에 걸리는 명령을 실행 | 도구가 실제로 가드를 부르는가 | 헤드리스로는 측정 불가(F9) → **3회차 대화형에서 그린** (§5) |

### 🔴 F9 — ⭐⭐ 발동 검증을 헤드리스로 대행하면 거짓 음성이 난다 (검증 수단의 한계 · 승격함)

③을 비대화형(헤드리스) 세션으로 대행하려 했더니 **훅이 아예 발동하지 않았다.**
대조 실험까지 전부 동일했다 — 훅이 대화형 세션에서 실제로 도는 것이 확인된 다른 폴더에서도,
중첩 실행 표식 환경변수를 제거해도, 헤드리스에서는 프로브 명령이 차단 없이 실행됐다.

이 결과의 위험은 방향이다. **연결이 멀쩡해도 "안 걸린다" 로 읽힌다** — 거짓 활성(F1)이
안심시키는 쪽이라면, 이건 검증 수단이 **멀쩡한 연결을 고장으로 판정**하는 쪽이다.
둘 다 뿌리는 같다: **검증 수단이 검증 대상을 실제로 보고 있는지부터 의심해야 한다.**

→ 절차 요구사항으로 승격 2건:
   **③ 발동 검증은 대화형 세션에서만 유효하다.** 헤드리스·자동화 경로로 대행하지 않는다.
   **프로브 명령은 훅이 죽어 있어도 무해한 형태로 고른다** — 이번 프로브는 dry-run 강제 푸시였다.
   훅이 발동하면 차단 메시지를 얻고, 발동하지 않아도 원격은 변하지 않는다.
   (무해하지 않은 프로브로 ③을 재면, 검증이 실패하는 순간 그 실패가 곧 사고다.)

### 🟡 F10 — 폴더 신뢰 승인이 훅 연결의 선행 조건이다 (문서 구멍 · 수정함)

에이전트 도구는 **신뢰 승인이 없는 폴더의 프로젝트 설정을 실행하지 않는다.**
대상 프로젝트가 그 상태였다(신뢰 플래그 미승인 실측). 즉 훅을 정확히 걸어도
**신뢰 승인 전에는 로드조차 되지 않을 수 있다** — `--status` 도 ② 프로토콜 검증도
이 상태를 보지 못한다. F9 가 헤드리스 경로를 전부 막아 이 항목 단독의 발동 실측은
분리하지 못했다 — ③ 대화형 재측정에서 함께 닫힌다.

→ 부트스트랩 §3 에 선행 조건으로 추가.

### F6 추가 실증 — 오탐 2회 추가 (누계 4회)

이번 재측정 중에도 기존 명령 문자열 가드가 2회 오탐 차단했다. 막힌 것은 이번에도 명령이 아니라
**판정 테스트 픽스처 문자열**과 **헤드리스 프로브에 넘길 프롬프트 문자열**이었다.
「명령 위치에서만 판정한다」 승격이 옳았다는 반복 실증. 우회는 매번 같았다 —
위험 문자열을 명령줄에서 파일 안으로 옮긴다.

## 5. ③ 발동 확인 — 그린 (3회차 방문 · 2026-08-14)

사용자가 대상 프로젝트에서 대화형 세션을 열어(폴더 신뢰 승인 포함) 프로브를 실행했다.
**결과: 하네스 가드의 deny 판정이 실세션에서 발동 — F2 닫힘.** 검증 사다리 ①②③ 전부 그린.

다만 곧바로 그린이 나온 게 아니다. **유효한 측정에 도달하기까지 무효 측정이 세 번** 있었고,
그 각각이 발견이다. 검증 수단이 검증 대상을 실제로 보고 있는지부터 의심해야 한다는
F9 의 교훈이 세 번 더 반복됐다.

| 시도 | 무엇을 했나 | 결과 | 왜 무효인가 |
| - | - | - | - |
| 1 | 가드가 **설치되지 않은 다른 폴더**에서 프로브 | 통과 | 미설치와 통과는 겉보기가 같다(F1과 같은 뿌리) |
| 2 | 대상 프로젝트에서 **`!` 직접 실행**으로 프로브 | 통과 | **F11** — 훅 경로를 타지 않는 실행 방식 |
| 3 | 에이전트 도구 호출로 강제 푸시 프로브 | **차단** | **F12** — 막은 주체가 하네스 가드가 아니었다 |
| 4 | 하네스 규칙에만 걸리는 무해 프로브 | **차단** | 유효 — 판정 메시지 서명으로 주체 확정 |

### 🔴 F11 — ⭐ 사용자 직접 실행(`!`)은 훅 경로를 타지 않는다 (검증 수단의 한계 · 승격함)

PreToolUse 훅은 **에이전트의 도구 호출**에 걸린다. 사용자가 `!` 접두어로 본인 권한으로
직접 실행하는 명령은 도구 호출이 아니라 훅이 아예 안 불린다. 대조 실증까지 됐다 —
**같은 명령이 `!` 로는 통과하고, 에이전트 호출로는 차단됐다.**

F9(헤드리스)와 같은 거짓 음성 부류다: 연결이 멀쩡해도 "안 걸린다" 로 읽힌다.
→ 절차 요구사항으로 승격: **프로브는 에이전트의 도구 호출로 실행한다.** 직접 실행으로 대행하지 않는다.

### 🔴 F12 — ⭐ 프로브 충돌 — deny 가 떠도 주체를 특정 못 할 수 있다 (검증 수단의 한계 · 승격함)

강제 푸시 프로브가 차단됐는데, 막은 것은 하네스 가드가 아니라 **이미 깔려 있던 전역의
다른 명령 가드**(F6 오탐을 냈던 그 가드)였다. 같은 패턴을 두 가드가 덮고 있으면
차단 메시지가 떠도 **어느 가드의 발동인지 특정할 수 없다** — 하네스 가드가 죽어 있어도
전역 가드가 막아 주므로, ③이 그린으로 오판된다. 거짓 양성이다.

→ 절차 요구사항으로 승격 — 프로브 선정 기준은 셋이다:
   ①**무해** (훅이 죽어도 아무것도 부서지지 않는다 — F9에서 확정)
   ②**대상 가드에만 걸린다** (같은 패턴을 덮는 다른 가드가 없는 규칙을 고른다)
   ③**판정 메시지의 서명으로 주체를 확인한다** (게이트 출력 계약 — "차단됨 — 이유 → 복구" 형식 —
   이 서명이 곧 발동 주체의 증명이다. 출력 계약을 고정한 것이 여기서 처음 값을 했다)

이번 확정 프로브 = **존재하지 않는 경로에 대한 소스 디렉토리 삭제 형태** — 하네스 규칙에만
걸리고, 가드가 죽어 실행돼도 지워질 것이 없다.
