## 1. 어휘를 먼저 가른다 — "승격" 은 두 개다

이 하네스에는 방향이 반대인 승격이 둘 있다. 같은 낱말로 섞으면 절차가 서로를 오염시킨다.

| | 방향 | 뜻 | 사는 곳 |
| - | - | - | - |
| **강도 승격** | `ask` → `deny` | 가드를 조인다 — 마찰 없음이 실측된 영역의 차단 강화 | 골격 1 승격 원칙 · 골격 2 절차 6 |
| **위임 승격** | `ask` → `allow` | 개입을 줄인다 — 습관적 승인만 남은 지점의 무인화 | **이 문서** · 로드맵 v2 |

**이 문서에서 "승격" 단독 표기 = 위임 승격이다.** 두 승격의 공통 원칙은 하나뿐이다 —
어느 방향이든 **실측된 영역만 옮긴다**(로드맵 「자율은 측정된 신뢰의 함수」).

## 2. 형태 — 판정은 자동, 적용은 사람 1회, 강등만 전자동

리서치 3 의 판정: "반복 승인을 학습해 무인 승격" 하는 구조는 조사한 어느 제품에도 없고,
실재하는 최대 자동화는 **제안까지**다(`/fewer-permission-prompts`). 반면 **강등은 데이터 기반
전자동이 실재한다**(auto 모드 3연속/누적20 fallback, Argo 자동 abort). 그 비대칭을 그대로 쓴다:

1. **판정(후보 산출) = 자동.** 리포트 명령이 §4 판정식으로 승격 후보를 근거 수치와 함께 낸다.
2. **적용 = `{승인 주체}` 의 1회 확인.** 확인의 실체는 §5 의 승격 레코드 작성이다.
3. **강등 = 자동·즉시.** 사람 확인을 기다리지 않는다(§6). 승격은 보수적으로, 강등은 실패 1건에.

## 3. 승격의 단위와 대상

- **단위 = 규칙 `id` × 저장소.** 로그의 `rule` 필드·접두사 정규화와 같은 단위다 —
  승격의 단위가 로그의 단위이고(리서치 3 §5 v1 표), 단위가 어긋나면 승격할 대상이 없다.
- **대상 = `ask` 규칙만.** ⚠️**`deny` 는 데이터가 아무리 쌓여도 승격 불가.** `deny` 의 정의가
  "되돌릴 수 없는 파괴"(골격 1 절차 1)라서다 — 무사고 이력은 가역성을 만들지 않는다.
  `deny` 를 옮기고 싶으면 그건 승격이 아니라 **규칙 재분류**(경계표·규칙 정의 수정, 사람의 정책 결정)다.
- **프로브(`probe: true`)는 전 판정에서 제외** — v1 과 동일.

## 4. 승격 판정식 — 구조는 여기 고정, 임계값은 슬롯

헌법 결정대로 **골격은 판정 구조만 갖는다.** 아래 4축의 구조는 이 문서가 고정하고,
`{N}`·`{T}`·`{M}` 값은 적용 프로젝트가 실측으로 채우며, 오탐률(v1 지표 4)이 과잉을 감시한다.

후보가 되려면 **4축 전부** 충족해야 한다:

| 축 | 조건 | 근거 선례 |
| - | - | - |
| 1 **연속 무거부** | 해당 규칙의 최근 `fire(ask)` 스트릭이 전부 승인이고 길이 ≥ `{N}`. 거부·이탈 1건이 카운터를 0 으로 리셋 | Argo `consecutiveSuccessLimit` · auto 모드의 리셋 카운터 |
| 2 **실패 한도 0** | 스트릭 판정에서 `fire(ask)` 뒤 `after` 부재 = **전부 실패로 센다.** v1 근사는 거부/이탈/훅 미발화를 구분 못 하는데, 그 구분 불가를 승격에 유리하게 해석하지 않는다 — 보수 방향 고정 | Argo `failureLimit` 기본 0 |
| 3 **습관적 승인 배제** | 스트릭의 응답 지연(`after.ts − fire.ts` 근사)이 **전부** `{T}` 미만이면 후보 부적격 — 마찰 없음이 아니라 "안 읽음" 의 신호로 판정하고 리포트에 사유를 표기 | auto 모드 전환의 근거(습관적 승인의 무가치) · §227.50 경보→전환 시간 |
| 4 **분산** | 스트릭이 `{M}` 개 이상의 서로 다른 날(또는 세션)에 걸친다 — 한 세션 몰아치기는 반복 승인이 아니라 한 번의 판단이다 | §227.50 의 분모 정신(총 주행 마일) |

리포트는 후보마다 **근거를 수치로 동봉**한다: 스트릭 길이·기간·지연 분포·같은 기간의 `pass` 분모.
점수 하나로 뭉개지 않는다 — 승인 주체가 확인하는 것은 점수가 아니라 근거다.

⚠️ 축 3 의 지연 근사에는 도구 실행 시간이 섞여 **지연이 과대측정된다.** 오차는 습관적 승인을
"놓치는" 방향이지 무고한 승인을 "몰아붙이는" 방향이 아니다 — 이 축의 부적격 판정은
"확실한 즉답 연속" 만 잡는 약한 필터임을 리포트에 표기한다. 정밀화는 §7.

**슬롯 판별 질문** (부트스트랩 워크시트와 같은 방식 — 값이 아니라 정하는 법):

- `{N}` — 그 규칙이 실사용에서 한 주에 몇 번 걸리나? 한 달 안에 도달 못 하는 `{N}` 은
  영구 `ask` 고착(골격 1 이 경고한 습관적 승인 경로)과 같고, 하루에 도달하는 `{N}` 은
  스트릭이 아니라 버스트다.
- `{T}` — 그 ask 의 판정 메시지를 실제로 읽고 판단하는 데 몇 초 걸리나? 본인이 1회 실측해서
  그 절반 아래를 즉답으로 본다.
- `{M}` — 그 명령이 나오는 작업 유형이 며칠에 한 번 돌아오나? 최소 2, 작업 주기가 길면 그 주기만큼.

⚠️ **판정 기준의 게이밍 방지** (§227.50 교훈): "무엇을 거부로 세는가"·4축의 구조를 바꿀 때는
이 문서의 결정 이력에 남기고, **바꾸기 전 로그와 혼합 집계하지 않는다.** `{N}` 을 낮춰
후보를 만드는 것은 승격이 아니라 기준 붕괴다 — 슬롯 값 변경도 레코드(§5)에 남긴다.

## 5. 승격 레코드 — 적용의 실체

승격은 설정 파일을 고쳐 `ask` 를 지우는 것이 **아니다.** 지우면 근거·강등 조건·관찰이 함께 사라진다.
승격의 실체는 **레코드 1건**이고, 가드가 판정 시 그것을 해석한다:

- 위치 = 대상 프로젝트 `.harness/promotions.jsonl`. ⚠️**`log.jsonl` 과 동일하게 반출 금지**
  (규칙 사유·프로젝트 고유값 포함) — 부트스트랩 `.gitignore` 단계에 함께 등록한다.
- 필드 = 규칙 `id` · 승격 시점 · `{승인 주체}` 확인 표식 · **근거 스냅샷**(스트릭 길이·기간·
  지연 분포 — 나중에 "왜 승격했더라" 를 로그 재집계 없이 답한다) · **강등 조건**(§6).
- ⭐**강등 조건 필드가 비어 있으면 레코드는 무효다** — 기계 검증 가능한 형태로,
  "강등 없는 승격 금지"(리서치 3 §5) 를 절차 준수가 아니라 **구조**로 강제한다.
- **가드의 해석**: 판정 시 유효한 레코드가 있으면 그 규칙을 `allow` 로 처리하되,
  **강등 조건 충족이 감지되면 레코드를 무시하고 `ask` 로 판정한다.** 강등에 설정 편집이
  필요 없다 = 자동·즉시(§2 형태 3)가 운영 규율이 아니라 코드 경로로 보장된다.
- **관찰은 끊기지 않는다**: 승격된 규칙의 매치도 계속 기록한다(`pass` 에 `rule`·`promoted` 표기).
  이벤트 5종의 **정의는 불변**이고("검사했으나 무발동 통과" 그대로) 필드 추가는 additive 다 —
  구현 시 `13-v1-eval-design.md` 결정 이력에 기록하고 진행한다. 기록 없는 allow 는
  분모(주행 마일)를 잃는다 — 강등 판정도, v3 무인 범위 산정도 그 분모 위에 선다.

## 6. 강등 — 승격과 쌍으로만 존재한다

기본 강등 조건 3종. **프로젝트가 조건을 추가할 수는 있지만 이 3종을 빼지는 못한다:**

- ⓐ **해당 규칙 관련 사고·오탐·거짓 그린 `note` 1건 → 즉시 실효.** 허용 실패 한도는 0 이고
  명시적으로만 올린다(Argo `failureLimit`) — 올린 사실 자체가 레코드에 남는다.
- ⓑ **`{승인 주체}` 의 수동 강등** — 사유를 `note` 로 남긴다.
- ⓒ **규칙 정의(패턴·id)가 바뀌면 자동 실효.** 바뀐 규칙은 다른 규칙이고,
  과거 스트릭은 그 규칙의 데이터가 아니다.

강등 후 재승격은 **스트릭 0 부터** 다시 시작한다. 강등 이력은 영구 보존하고, 재승격 확인 때
승인 주체에게 이전 강등 사유를 표시한다 — 같은 규칙이 승격↔강등을 반복하면 그것은
규칙이 아니라 경계표가 잘못 그어졌다는 신호다(골격 2 "애매하면 ask" 로 되돌린다).

승격·강등 **사실 자체도 로그에 남는다** — `note` 라벨 `promoted` / `demoted`
(적용·확인의 주체가 사람이므로 `note` 의 정의와 정합, 이벤트 5종 불변).

## 7. v1 근사의 한계가 승격에 작용하는 방식

| v1 의 구분 불가 | 승격 판정에서의 처리 | 방향 |
| - | - | - |
| 영구 승인 / 1회 승인 | 전부 "승인 1회" 로만 센다 | 중립 |

`tool_decision` 연동(사람 응답 4갈래 — 필드명 호환은 v1 스키마가 이미 확보). ⚠️연동 전후의
데이터는 혼합 집계하지 않는다 — 근사 스트릭과 정밀 스트릭은 다른 자다.

## 9. 이 문서가 다루지 않는 것

로드맵의 v2(위임 확대)는 이 문서보다 넓다 — **역할 경계(골격 3)·품질 사이클(골격 6)의 코드화,
인계 체크리스트의 스키마 승격**은 별도 설계다. 이 문서는 그중 "습관적 승인만 남은 `ask` 의
승격" 하나를 고정한다. v2 전체의 완료는 로드맵의 정의대로 "개입 없이 완주한 작업 비율 상승의
실측" 이며, 그 분모·분자가 바로 §5 가 끊기지 않게 지킨 관찰 기록이다.

장기 참고: 업계는 ask 축적→규칙 승격이 아니라 **실시간 판정 모델로 ask 를 대체**하는 길로 갔다
(리서치 3 §3). 이 하네스의 가드는 보안 경계가 아니라 실수 방지 장치라 규칙 승격 경로가 여전히
유효하지만, **v3 자율 루프 설계 시 "ask 총량을 줄이는 제3의 길" 로 재검토한다** — 그 재검토가
이 문서의 결정을 뒤집으면 결정 이력에 남기고 뒤집는다.
