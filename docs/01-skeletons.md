# 골격 목록

각 골격은 **슬롯 · 절차 · 실패 시나리오** 3종을 갖는다(번역 규율 §4).
③이 비어 있으면 미완성으로 표시하고, 채워질 때까지 "완성" 으로 세지 않는다.

## 골격 공통 규약 (패널 반문 v0 반영)

1. **슬롯마다 판별 질문을 함께 적는다.** 슬롯 이름만 있으면 처음 채우는 사람이 기준을 못 세운다.
   `{X}` 옆에 "무엇을 보고 정하는가" 를 한 줄로 붙인다.
2. **게이트 성격의 골격은 복구 경로를 갖는다.** 판정 메시지가 **"무엇을 하면 통과하는가"** 를 담아야 한다.
   ⭐ 게이트가 꺼지는 실제 경로는 이것이다 — 막혔는데 할 일을 모르면 사람은 규칙이 아니라 **가드를 끈다.**
3. **한계를 스스로 밝힌다.** 무엇을 못 잡는지 쓰지 않으면 읽는 사람이 보증으로 오해한다.
   오해된 보증은 없는 것보다 나쁘다.
4. **활성 확인 수단을 갖는다.** "동작하다 죽음" 과 별개로 **"애초에 설치 안 됨"** 을 감지해야 한다.
   미설치는 통과와 구별되지 않는다.
5. **승인이 필요한 지점에는 `{승인 주체}` 슬롯을 둔다.** "협의한다" 는 절차가 아니다.

| # | 골격 | 상태 |
| - | - | - |
| 1 | 위험 명령 가드 | 패널 반영 · **P1 대기** |
| 2 | 경계표 기반 test-first 가드 | 패널 반영 |
| 3 | 역할 경계 | 패널 반영 · **P3 대기**(인계 형식) |
| 4 | 드리프트 감시 | 패널 반영 |
| 5 | 문서 규약 게이트 | 패널 반영 |
| 6 | 품질 사이클 | 패널 반영 · **P2 대기**(경량 경로) |
| 7 | 배포 기계 | 패널 반영 |

> "명세 완료" = 슬롯·절차·실패 시나리오가 적혔다. **구현 완료가 아니다.**
> P1~P3 = 정책 결정 대기 항목. `docs/03-panel-review-v0.md` §3 참조.

## 1. 위험 명령 가드

되돌릴 수 없는 명령을 실행 전에 잡는다.

**슬롯**
- `{파괴 명령 패턴}` — 판별 질문: **"실행 후 5분 안에 원상복구할 수단이 있나?"** 없으면 후보다.
- `{공유 리소스 판별}` — 판별 질문: **"이 대상을 나 말고 누가 동시에 쓰나?"**
  ⚠️ 호스트 이름으로 판별하지 않는다. 프록시·터널·포트 포워딩을 경유하면 이름이 로컬처럼 보인다.
  **연결이 최종적으로 닿는 곳**으로 판별한다.
- `{승인 필요 작업}` — 판별 질문: "정규 절차인데 데이터가 사라지는가?"
- `{승인 주체}` — 누구의 승인인가. "협의한다" 는 절차가 아니다.

**절차**
1. 판정을 **두 단계 어휘로 고정**한다.
   - `deny` — 되돌릴 수 없는 파괴. 사람이 직접 하거나 규칙을 고쳐야 한다.
   - `ask` — 정규 절차인데 데이터가 사라진다. 사람이 그 자리에서 정한다.
2. **읽기와 쓰기를 가른다.** 조회·준비·검증은 막지 않는다. 막으면 가드가 미움받고 꺼진다.
3. **실행 맥락에서만 판정한다.** 같은 문자열이 문서·커밋 메시지·검색 패턴 안에 있을 때는 통과시킨다.
4. **가드가 죽으면 반드시 보이게 한다.** 파서·런타임이 없어 판정을 못 하면 조용히 통과시키지 말고 알린다.
5. 차단 게이트는 **fail-closed**, 조언 게이트는 **fail-open**. 성격을 먼저 정하고 나서 구현한다.
6. **복구 경로를 판정 메시지에 넣는다.** `deny` 를 만난 사람이 할 수 있는 것은 셋뿐이다 —
   ①다른 방법으로 목적 달성 ②사람이 직접 실행 ③규칙 수정. **어느 것을 권하는지 메시지가 말해야 한다.**
7. **활성 확인** — 게이트가 설치돼 있는지 자체를 주기적으로 확인한다.
   설정을 한 번 빠뜨리면 게이트 전체가 조용히 없는 상태가 되고, 그건 "위반 없음" 과 똑같이 보인다.

**한계 (반드시 함께 적는다)**
- 패턴 판정은 **변수 치환·개행·별칭으로 우회된다.** 이건 **보안 경계가 아니라 실수 방지 장치**다.
  악의를 막는 용도로 쓰면 안 되고, 그렇게 소개해서도 안 된다.
- 판정 단위가 명령 문자열이라, 스크립트 파일 안에 든 명령은 보지 못한다.

**실패 시나리오**
- 전역 데몬 종료 명령 하나가 **다른 작업 공간에서 돌던 프로세스까지** 내렸다.
  → 전역 영향 명령은 대상을 특정할 수 있을 때만 허용한다.
- 조회는 자유롭게 하라고 규칙을 느슨하게 뒀더니 **공유 환경에 쓰기 구문이 그대로 나갔다.**
  → "공유 대상 + 쓰기 구문" 의 **교집합**으로 판정해야 한다. 둘 중 하나만으로는 과잉·과소가 된다.
- 가드가 파서 부재로 조용히 통과하고 있었는데 **몇 주 동안 아무도 몰랐다.**
  → 침묵은 통과와 구별되지 않는다.

## 2. 경계표 기반 test-first 가드

"테스트를 먼저 쓸 가치가 있는 영역" 에서만 test-first 를 강제한다.

**슬롯**
- `{경계표}` — 어느 경로가 `deny`(예외 없음) / `ask`(사람이 판단)인가
- `{테스트 탐색 규칙}` — 대상 파일에 대응하는 테스트를 어떻게 찾는가
- `{탈출구 이름}` — 가드를 끄는 환경변수

**절차**
1. **경계표의 SSOT 는 문서**로 두고, 가드는 **그 표를 기계화한 것**으로만 존재한다.
   표가 바뀌면 가드를 함께 고친다. 가드에만 있는 규칙은 만들지 않는다.
2. **`--audit` 을 먼저 돌린다.** 켜기 전에 "경계 안인데 테스트가 없는" 파일이 몇 건인지 센다.
   숫자를 모르고 켜면 첫날 전부 막힌다.
3. `deny` 는 **편차 없는 영역에만**. 계산 로직과 얇은 래퍼가 섞인 곳은 `ask` 로 둔다.
4. **테스트 파일 자신은 항상 통과**시킨다. Red 를 못 쓰면 가드가 자기모순이다.
5. **탈출구를 문서에 명시**한다. 대량 리팩터링에서 가드가 인질이 되면 안 된다.
6. **단계적으로 도입한다.** `--audit` 으로 세고 나서 무엇을 할지가 절차의 절반이다.
   ```
   측정  --audit 으로 기존 위반 건수를 센다
     ↓
   유예  기존 파일은 통과시킨다(신규·수정 파일만 판정) — 첫날 전부 막히면 가드는 그날 꺼진다
     ↓
   적용  신규 코드에만 적용해 한동안 돌린다
     ↓
   승격  마찰이 없다고 확인된 영역만 ask → deny 로 올린다
   ```
7. **복구 경로**: 막힌 사람이 할 일은 "Red 를 먼저 쓴다" 하나뿐이다. 메시지가 **경계표 위치까지** 알려줘야
   사람이 "이 파일이 왜 대상인지" 를 확인하고 표를 고칠 수 있다.
8. **활성 확인** — 스크립트가 로드조차 안 되는 상태를 감지한다(아래 실패 시나리오 참조).

**한계 (반드시 함께 적는다)**
- 테스트의 **존재**만 본다. 그 테스트가 의미 있는지, 실제로 그 로직을 덮는지는 보지 않는다.
  존재 판정을 커버리지 보증으로 읽으면 안 된다.
- 경로 매칭은 디렉토리 단위 근사라, 같은 디렉토리 안의 편차를 구분하지 못한다.

**실패 시나리오**
- 디렉토리 단위로 근사한 `deny` 를, 파일 단위 기준이 필요한 영역에 걸었더니
  **십여 줄짜리 얇은 함수에까지 "가드 통과용 껍데기 테스트" 를 쓰게 됐다.** 그 테스트는 리팩터링만 막는 짐이다.
  → 애매하면 `ask`.
- 스크립트가 모듈 시스템 차이로 **로드조차 안 된 채 조용히 통과**하고 있었다.
  → 가드는 "동작하지 않음" 과 "위반 없음" 을 반드시 구분해 보고해야 한다.

## 3. 역할 경계

에이전트를 능력이 아니라 **경계**로 나눈다. 도메인과 무관해 가장 이식성이 높다.

**슬롯**
- `{역할별 도구·명령}` — 각 역할이 실제로 실행하는 것
- `{역할별 권한}` — 판별 질문: **"이 역할이 쓰기를 할 수 있으면 경계가 무너지나?"** 그렇다면 읽기 전용으로 준다.
- `{경계표}` — 어떤 요청이 어느 역할인가
- `{인계 형식}` — 앞 역할이 뒤 역할에 무엇을 넘기는가 · **형식 미정(P3 확정 대기)**

**절차 — 3원칙**

| 원칙 | 나누는 쌍 | 막는 것 |
| - | - | - |
| **설계자 / 집행자** | 무엇을 바꿀지 정하는 쪽 ↔ 정해진 것을 정확히 찍는 쪽 | 아직 안 정해진 것을 기계적으로 확정해 버리는 것 |
| **작성자 / 판정자** | 테스트를 쓰는 쪽 ↔ 그린/레드를 판정하는 쪽 | 자기가 쓴 기준으로 자기를 통과시키는 것 |
| **감사자 / 적용자** | 드리프트를 찾는 쪽(읽기 전용) ↔ 고치는 쪽 | 고치면서 찾느라 무엇이 원래 어긋나 있었는지 잃는 것 |

추가 규칙:
1. 모든 역할 정의에 **`USE WHEN` / `SKIP for → 대신 누구`** 를 함께 쓴다.
   라우팅 충돌은 설명을 늘려서가 아니라 **배제를 명시해서** 푼다.
2. **감사자는 쓰기 도구를 갖지 않는다.** 권한으로 경계를 강제해야 경계가 유지된다.
3. 상위 조율자는 **에이전트가 아니라 플레이북**이다. 하위가 하위를 다시 부를 수 없기 때문이다.

**실패 시나리오**
- 판정자를 따로 두지 않았더니 **구현한 쪽이 "통과했다" 고 보고**했고, 실패한 항목은 다음 단계에서 드러났다.
- 역할 설명에 `USE WHEN` 만 있고 `SKIP for` 가 없어, **비슷한 역할 셋이 같은 요청을 서로 먹었다.**

## 4. 드리프트 감시

같은 내용으로 두기로 한 것들이 조용히 어긋나는 것을 잡는다.

**슬롯**
- `{미러 쌍}` — 어떤 파일이 어디와 같아야 하는가
- `{배치 정책}` — 자산마다 전역 / 프로젝트 / 배포본 중 어디에 두는가

**절차**
1. **감시 대상 목록을 자산으로 승격**시킨다. 스크립트에 하드코딩하면 자산이 늘어도 목록이 안 늘어난다.
2. 자산마다 **배치를 선언**한다. 선언되지 않은 위치에 놓인 자산은 **아무도 감시하지 않는다.**
3. **"내용 동일" 과 "존재만 동일" 을 구분**한다. 실행 위치에 따라 경로 표기가 달라지는 자산은
   내용 비교가 오탐이 된다. 그런 자산은 **미러이되 동일할 수 없는 유형**으로 따로 분류한다.
4. 줄바꿈 정규화 후 비교한다. 개행 차이는 드리프트가 아니다.
5. 상대가 없으면 **조용히 no-op** 한다. 감시 도구가 배치 전제를 강요하면 안 된다.
6. **양방향으로 본다.** 배포본이 낡은 경우만 보면, **원본이 낡은 역방향**을 영원히 놓친다.
7. ⭐ **승인된 차이와 새 차이를 구분한다.** 의도된 비대칭(§3 의 "미러이되 동일할 수 없는 유형")을
   매번 경고하면 사람은 곧 전체를 무시한다. 승인된 차이는 목록에 기록해 조용히 두고,
   **목록에 없는 차이만** 알린다. 경고 피로는 감시 도구의 주된 사인이다.

**복구 경로**: 경고에는 **어느 쪽을 정본으로 볼지** 판단할 정보(양쪽 경로·최종 수정 시점)를 함께 준다.
"다릅니다" 만으로는 어느 쪽을 고칠지 모른다.

**실패 시나리오**
- 감시 스크립트가 **한쪽 디렉토리만 스캔**하고 있었다. 그래서 다른 위치에만 추가된 자산은
  **감시망에 영원히 안 들어왔다.** 도구는 계속 "이상 없음" 을 보고했다.
  → 감시 범위와 자산 배치가 어긋나면 침묵이 곧 거짓 그린이다.
- 미러 목록이 특정 파일 여섯 개로 하드코딩돼 있어, 나중에 추가된 종류는 **한 번도 비교되지 않았다.**

## 5. 문서 규약 게이트

문서가 코드보다 먼저 낡는 것을 막는다.

**슬롯**
- `{상시 문서 경로}` — 판별 질문: **"이 문서가 틀리면 누군가 잘못된 작업을 하나?"** 그렇다면 상시다.
- `{이력 보관 경로}` — 시점 박제. 낡아도 되는 곳

**서술적 / 규범적 판별** — 문서와 코드가 어긋났을 때 어느 쪽을 고칠지의 기준이다.

| 질문 | 서술적 | 규범적 |
| - | - | - |
| 이 문서는 무엇을 하나 | **코드가 이렇게 동작한다고 기록** | **이렇게 동작해야 한다고 요구** |
| 예 | 아키텍처 설명, 진행 상태, README | 명세, 요구사항, 성공 기준, 정책, 계약 |
| 어긋나면 | **코드가 옳다** — 문서를 고친다 | **코드의 미이행을 먼저 의심**한다 |
| 문서를 고치려면 | 그냥 고친다 | **정책 변경**이므로 근거와 합의가 필요하다 |

⚠️ 명세를 구현에 맞춰 고쳤다면 **그 판정 근거의 유효기간을 확인한다.**
"지금 설정이 이러니 이 조항은 발동하지 않는다" 류의 근거는, 같은 주기의 다른 변경이 바로 무너뜨린다.

**절차 — SSOT 3원칙**
1. **한 사실은 한 곳.** 같은 표를 두 문서에 복제하지 않는다. 두 번째 문서는 링크한다.
2. **코드가 SSOT 인 값은 문서에 쓰지 않는다.** 상수값·개수·시그니처는 **값 대신 위치**를 적는다.
   ⚠️ **줄 번호로 가리키지 않는다 — 심볼 이름으로 가리킨다.** 줄 번호는 다음 커밋에 틀린다.
3. **현행과 이력을 분리한다.** 항상 읽히는 문서에는 현행 + 재발 방지만. 경위는 하단 `이력` 절이나 보관 경로로.
   단 **"이건 하지 마라" 형태의 이력은 본문에 남긴다** — 격리 대상은 지난 경위, 유지 대상은 금지 사항이다.

집행:
- 상시 문서에 **새로 추가된** 줄 번호 참조만 잡는다(기존 위반은 grandfather — 재경고는 소음이다).
- 이력 보관 경로는 검사 대상에서 뺀다. 그곳의 줄 번호는 정당하다.

**실패 시나리오**
- 문서와 코드가 어긋났을 때 **어느 쪽이 틀렸는지 판정 기준이 없어** 코드를 문서에 맞춰 되돌렸다.
  → 서술적 문서(코드가 이렇게 동작한다는 기록)는 **코드가 옳다**. 규범적 문서(명세·정책·계약)는
    **코드의 미이행을 먼저 의심**한다. 명세를 구현에 맞춰 고치는 건 정책 변경이라 근거와 합의가 필요하다.
- 항상 컨텍스트에 실리는 문서가 **가장 오래 낡아 있었다.** 감사 범위에서 빠져 있었기 때문이다.
  → 자동 로드 문서를 감사 범위에 **명시적으로** 포함한다.

## 6. 품질 사이클

구현부터 보고까지의 단일 표준 흐름. **일반론은 넣지 않는다**(번역 규율 §1).

**슬롯**
- `{BUILD_CMD}` · `{UNIT_TEST_CMD}` · `{E2E_CMD}` · `{LINT_CMD}`
- `{측정 규율}` — 판별 질문: **"같은 커밋을 두 번 재면 결과가 같은가?"** 다르면 그 지점을 적는다.
- `{보고 형식}` — 무엇을 반드시 담는가(변경·검증 수치·건너뛴 단계·남은 것)
- `{승인 주체}` — 명세 확정과 되돌릴 수 없는 단계의 승인자

**절차**
1. **명세 확정** — 제품 결정이 걸려 있으면 코드부터 만들지 않는다. 선택지를 표로 묶어 한 번에 묻는다.
2. **구현** — 변경 파일 표를 남긴다.
3. **단위·회귀** — 결과는 **숫자로**(`N/N`). 변경 모듈뿐 아니라 영향 범위까지.
4. **통합/E2E** — 실패는 **먼저 분류**한다. 분류 기준은 다음 순서로 본다.

   | 신호 | 분류 |
   | - | - |
   | 재시도에서 통과한다 | **비결정성** — 즉시 픽스 대상에서 뺀다. 다만 기록은 남긴다 |
   | 변경 전 커밋에서도 같은 조건에서 실패한다 | **원래 결함** — 이번 변경의 회귀가 아니다 |
   | 기대값이 이번 변경의 의도와 어긋난다 | **명세 불일치** — 테스트를 고친다 |
   | 위 셋이 아니다 | **회귀** — 코드를 고친다 |

   ⚠️ **분류 없이 "실패=회귀" 로 코드를 되돌리지 않는다.** 이 순서를 건너뛰면 정상 변경을 지운다.
5. **보고** — 변경·검증 결과·부수 발견·남은 것. 건너뛴 단계가 있으면 **건너뛰었다고 쓴다.**

측정 규율(어느 프로젝트에나 적용):
- **단일 실행으로 기준선을 확정하지 않는다.**
- **판정 대상과 기준선은 같은 조건에서 잰다.** 전체 실행분과 부분 실행분을 비교하지 않는다.
- **측정 중에는 다른 작업을 병행하지 않는다.** 부하가 곧 결과다.
- **실패가 광범위하면 회귀보다 환경·연쇄를 먼저 의심한다.**
- ⚠️ **명령 출력을 파이프로 넘기지 않는다.** 종료코드가 파이프 끝 명령의 것이 되어 실패를 통과로 읽는다.
  결과는 리포트 파일이나 결과 줄로 확정한다.

**실패 시나리오**
- 통합 테스트 실패 수가 실행마다 크게 달랐다. 원인은 **실패 시 아티팩트 덤프가 정리 단계를 타임아웃 너머로
  밀어 무관한 후속 테스트까지 연쇄로 죽인 것**이었다. 그 허수 기준선을 믿고 **정상 변경을 회귀로 오판해
  되돌렸다가** 재판정에서 뒤집혔다. → 대기 시간을 늘리는 방향은 악화시킨다. 덤프를 줄이고 재시도로 가른다.
- "잘 됐다" 만 보고하고 건너뛴 단계를 적지 않아, **미검증 상태가 완료로 집계**됐다.

## 7. 배포 기계

하네스 자체를 버전 있는 산출물로 배포하고, 낡음을 감사한다.

**슬롯**
- `{배포 채널}` — 판별 질문: **"사용하는 쪽이 갱신을 어떻게 받아 가나?"** 그 경로가 채널이다.
- `{매니페스트}` — 버전·구성 개수를 적는 곳
- `{승인 주체}` — 버전을 올려 배포하는 것을 누가 승인하는가

**한계**: 이 골격은 **채널이 하나라고 가정**한다. 채널이 둘 이상이면 감사·정합 절차가 채널 수만큼 늘어난다.
두 번째 채널을 실제로 만나기 전까지는 일반화하지 않는다 — 상상으로 판 슬롯은 맞은 적이 없다.

**절차**
1. **감사 → 승인 → 적용 → 매니페스트 정합 → 검증** 순서로 돈다. 감사와 적용을 같은 단계에서 하지 않는다(골격 3).
2. 감사는 **양방향**으로 본다. 배포본이 낡은 경우뿐 아니라 **원본이 낡은 경우**도 있다.
3. 매니페스트의 **개수·버전이 실제와 맞는지**를 검증 단계에 넣는다. 사람이 안 읽는 곳이라 가장 오래 틀려 있다.
4. **매니페스트는 유출 검사 대상**이다(번역 규율 §5-2). author·homepage·repository 필드가 마지막까지 남는다.

**실패 시나리오**
- 배포본의 절차 문서가 **존재한 적 없는 환경변수**를 실행 조건으로 지시하고 있었다.
  지시를 그대로 따르면 해당 트랙을 건너뛰고 **"전부 통과" 로 보고**하게 된다 — 거짓 그린이다.
  → 절차 문서가 참조하는 스위치·경로는 감사 항목에 포함한다.
- 규율 하나가 **배포본 전체에 한 번도 등장하지 않아**, 판정자 역할이 잘못된 기준으로 판정하고 있었다.
  → 감사는 파일 대조뿐 아니라 **"있어야 할 규율이 있는가" 로도** 본다.
