## 1. v1 은 무엇이고, 무엇이 아닌가

**v1 = 기존 게이트의 판정 결과를 구조화된 로그로 남기고, 그 로그에서 지표를 산출하는 층.**
새 판정기를 만들지 않는다 — 완주 판정기는 이미 있다(골격 2 의 테스트가 곧 검증기,
리서치 1 원칙 1). v1 이 하는 일은 셋뿐이다:

1. 골격들이 판정하는 순간에 **이벤트 한 줄을 기록**하게 한다 (로그 층).
2. 쌓인 로그에서 **지표 5종을 한 명령으로 산출**한다 (리포트 명령).
3. 같은 작업 유형을 반복 측정해 **기준선**을 만든다 — v2 승격("개입 없음이 실측된
   영역만 무인 승격")의 근거 데이터가 이것이다.

v1 에 **넣지 않는 것** (경계):

- **승격·강등의 자동 판정** — v2 다. 단, v2 가 판정에 쓸 필드(후속 행동·분모)는 지금 스키마에
  고정한다. 스키마를 나중에 바꾸면 그전 데이터가 통째로 오염된다(§227.50 교훈, 리서치 3 §5).
- **LLM 판정 지표**(risk/autonomy score 류) — 1인 규모에서는 표본이 작아 사람 전수 라벨이
  더 싸고 정확하다 (리서치 1 §3).
- **루프·예산 감시 골격 신설** — 리서치 2 빈 곳 ①④는 실물 조건(장시간 무인 실행)이 아직 없다.
  상상으로 슬롯을 파지 않는다는 원칙(골격 7 의 한계 서술)대로, v3 진입 전 재검토로 미룬다.
- **거짓 그린 감사의 자동화** — 사람 표본 감사만 현실적이다(리서치 1 분류표). 절차만 §6 에 둔다.

## 2. 이벤트 정의 — 무엇을 세는가

⚠️ **이 절이 이 문서의 심장이다.** CA DMV 보고제의 실패는 "무엇을 개입으로 세는가" 를 각자
정의하게 둔 것이었다(리서치 3 §4) — 정의가 흔들리면 지표 비교가 오염된다. 정의는 여기 고정하고,
바꿀 때는 결정 이력에 남긴 뒤 **그전 로그와 섞어 집계하지 않는다.**

| 이벤트 | 정의 | 기록 주체 |
| - | - | - |
| `fire` | 게이트가 deny 또는 ask 판정을 **낸** 것. 프로브 발동도 `fire` 다(`probe: true` 로 구분) | 각 골격, 판정 직후 |
| `pass` | 게이트가 명령을 **검사했으나 무발동** 통과시킨 것 — 지표의 분모 | 각 골격, 통과 직후 |
| `after` | ask 발동 뒤 **같은 도구 호출이 실제 실행된** 것 — 사람이 승인했다는 행동적 신호 | PostToolUse 훅 |
| `audit` | 골격 2 `--audit`·골격 4 실행의 수치 스냅샷 (전체/경계 안/미달 건수, 새 차이/승인된 차이) | 해당 골격 |
| `note` | 사람이 손으로 남기는 라벨 — 오탐 확정, 거짓 그린 감사 결과, 부트스트랩 소요 시간 | 사람 (CLI 로) |

**관찰 한계를 정의에 포함한다.** 훅은 판정을 내는 곳까지만 본다 — ask 이후 사람의 응답
4갈래(영구 승인/1회 승인/거부/이탈, 리서치 3 의 `tool_decision`)를 하네스가 직접 볼 수 없다.
v1 의 근사: **`fire(ask)` 뒤 `after` 가 있으면 승인, 없으면 "거부 또는 이탈"**(둘은 구분 불가).
이 구분이 필요해지면 Claude Code OTel `tool_decision` 연동으로 보완한다 — 스키마 필드명을
그쪽과 호환되게 지어 두는 이유다. **근사를 정밀 관찰인 것처럼 집계하지 않는다** —
리포트는 "거부/이탈(구분 불가)" 로 표기한다.

## 3. 로그 스키마

**형식: JSONL, 한 판정 = 한 줄, append 전용.** 위치는 적용 대상 프로젝트의
`.harness/log.jsonl` — **하네스 저장소가 아니라 대상 프로젝트에 산다.**

⚠️ **로그 파일은 반출 금지 대상이다.** 규칙 사유(`why`)와 명령 접두사에 대상 프로젝트의
고유값이 들어간다. 공개되는 것은 이 문서의 **스키마뿐**이고, 데이터는 각 프로젝트에 남는다.
부트스트랩 절차에 `.gitignore` 등록을 포함한다(대상 프로젝트가 사내 저장소라도 —
로그와 코드는 수명이 다르다).

```jsonc
{
  "ts": "2026-08-18T06:00:00Z",   // 시점
  "session": "…",                  // 세션 식별자 (환경이 주면; 없으면 생략)
  "event": "fire",                 // §2 의 5종
  "gate": "danger-guard",          // 어느 골격이
  "rule": "no-history-rewrite",    // 어느 규칙이 (규칙에 id 를 부여한다 — §5)
  "decision": "deny",              // deny | ask (fire 일 때만)
  "probe": false,                  // 검증 전용 프로브 발동인가 (F13)
  "cmdPrefix": "git push",         // 정규화된 명령 접두사 — 원문이 아니다 (아래)
  "outcome": null                  // after 상관용 도구 호출 식별자 (있으면)
}
```

**원문 명령을 저장하지 않는다.** 리서치 3 의 결론 — 승격의 단위는 명령 접두사 × 저장소이므로
로그 단위도 그것이다. 원문은 승격 판정에 불필요하고, 로그 반출 사고가 나도 접두사만으로는
피해 폭이 작다. 접두사 정규화 = **첫 토큰 + 첫 서브커맨드**(`/fewer-permission-prompts` 와
같은 묶음 단위).

`audit` 이벤트는 `rule`·`decision` 대신 수치 필드를 갖는다
(예: `{ total: 311, inScope: 39, missing: 29 }`). `note` 는 자유 서술 `text` 와
`label`(`false-positive` | `false-green` | `bootstrap-minutes` | `fp-reviewed` | …)을 갖는다.
`fp-reviewed` 는 **판정 경계표**다 — 그 `ts` 이전의 발동(`rule` 이 있으면 그 규칙만)은 사람이
전수 판정했다는 사실만 말하고, 오탐 여부는 말하지 않는다(오탐 확정은 `false-positive` 로 따로).
`rule` 을 실어도 승격을 실효시키지 않는다(강등 라벨 어휘 밖).

## 4. 지표 5종 — 수집 지점 매핑

리서치 1 §3 의 최소 지표 집합을 이 하네스의 실제 수집 지점에 묶는다.

| # | 지표 | 산출 | 상태 |
| - | - | - | - |
| 1 | **작업 완주율** — 검증 게이트 그린으로 종료한 작업 비율 | `audit`(골격 2) 시계열 — 미달 건수가 0 으로 닫힌 작업 / 전체 | v1 에서 수집 시작 |
| 2 | **개입 분해** — 게이트 발동 후 사람의 반응 | `fire(ask)` × `after` 상관 — 승인 / "거부·이탈(구분 불가)" | 근사 수집 (§2 한계) |
| 3 | **개입 간 시간** | 인접 `fire` 간 `ts` 차이 | 자동 |
| 4 | **게이트 발동 + 오탐률** — 발동 중 잘못 막은 비율 | 분자 = `note(false-positive)`, 분모 = `fire` 수. 발동이 드물어(v0 실측 세션당 0~수 건) **전수 라벨이 가능하다** | 발동 자동 · 라벨 사람 |
| 5 | **비용/작업** — 부트스트랩 소요 등 | `note(bootstrap-minutes)` + `pass`/`fire` 총량 | 실측 1점 존재 (7분 — 기준값 30분 대비. 1회차는 미계측) |

**v0 이 산문으로 남긴 것을 구조화하는 것이 첫 이관 작업이다** — 필드 리포트 1·2 의
발동 기록·부트스트랩 시간을 `note` 로 소급 기록하면 기준선의 첫 점이 된다(리서치 1 §3 끝).

지표 2 의 완전한 3분해(ⓐ사람이 끊음 ⓑ에이전트가 물음 ⓒ권한 응답)는 세션 로그가 필요해
v1 범위 밖이다 — ⓒ만 위 근사로 수집하고, ⓐⓑ는 필드 리포트의 산문 기록을 유지한다.
축소를 숨기지 않는다: 리포트 명령은 미수집 지표를 "미수집" 으로 표기한다(골격 공통 규약 4 —
안 잰 것과 0 은 다르다).

## 5. 프로브 슬롯 정식화 (F13 승격)

필드 리포트 2 F13 — 기존 가드가 있는 프로젝트에서는 프로브 3기준(무해·대상 가드에만
걸림·서명 확인)을 만족하는 실규칙이 없다. 임시 해법(표식 문자열 deny)을 골격 1 의 정식
슬롯으로 승격한다:

- 설정에 `dangerGuard.probe` 를 둔다 — 아무것도 막지 않는 검증 전용 표식 규칙.
- `--status` 는 프로브를 **실규칙 수와 분리해 센다** ("deny 3 · ask 2 · 프로브 1").
  실규칙 0 + 프로브 1 은 `empty` 다 — 프로브가 규칙 수를 채워 `active` 로 보이면
  거짓 활성(F1)의 재발이다.
- 프로브 발동은 로그에 `probe: true` 로 남아 지표 4 의 분자·분모에서 **제외**된다.
- 규칙에 `id` 를 부여한다(없으면 패턴 문자열로 대체) — 로그의 `rule` 필드가 이것이다.

## 6. 사람 판정이 남는 두 곳 — 절차

리서치 1 의 결론대로 사람 판정은 둘만 남긴다. 둘 다 `note` 이벤트로 로그에 합류한다.

1. **오탐 확정 라벨** — 발동 건을 훑고 "잘못 막았다" 를 확정한다. 발동이 드무니 전수.
   판정 기준: 발동이 없었어야 했나(규칙이 과잉) — 우회했는가가 아니라 **규칙이 옳았는가**.
   판정을 마치면 오탐이 0 건이어도 **`--note fp-reviewed [--rule <id>]` 로 경계표를 남긴다** —
   이것이 없으면 리포트는 그 발동들을 "미판정" 으로 표기한다(라벨 0 ≠ 오탐 없음).
   오탐이 **규칙 정의 수정**으로 이어졌다면(규칙은 프로젝트 소유 — 골격은 손대지 않는다),
   경계표를 남기기 전에 **판정한 원문 전체에 수정 규칙을 재적용**한다: 오탐으로 확정한 건만
   통과하고 정탐은 전부 그대로 막혀야 수정 범위가 맞다. 하나라도 정탐이 풀리면 과잉 수정이다.
2. **거짓 그린 표본 감사** — 게이트는 통과했지만 실제로는 미완인 경우(reward hack 의 로컬판).
   METR 방식: 전수가 아니라 **의심 플래그가 뜬 것만** — v1 의 플래그 = `audit` 수치가
   비정상적으로 빨리 닫힘, 또는 완주 직후 같은 영역의 재작업 발생.

## 판정 — v1 완주 (2026-08-20)

**다섯 기준 전부 그린.** 마지막까지 남았던 기준 1 이 3회차 설치처의 실사용에서 닫혔다 —

접두사)은 §3 의 반출 금지 규칙대로 대상 프로젝트의 로그에만 남기고 여기엔 건수만 적는다.

⚠️ **기준이 말하지 않은 것을 달성했다고 읽지 않는다** (`07-v0-done.md` 와 같은 규칙):

  여전히 "미수집" — 실사용이 더 쌓여야 채워진다.
- **발동 2건의 오탐 여부 — 판정 완료 (2026-08-20 추기).** §6 절차 1 대로 전수(2건)를
  사람이 판정했다: 둘 다 규칙 의도에 부합하는 정탐, 차단 후 정상 경로로 복구 확인 —

  기록이 이 note 다 — 오탐 확정용 `false-positive` 라벨만으로는 이 구분이 로그에 안 남는다.
