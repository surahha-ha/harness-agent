# 필드 리포트 2 — 짝 저장소 프로젝트 적용

1회차와 다른 조건을 고르려고 잡은 대상이다. **두 저장소로 나뉜 업무 시스템의 프론트엔드 쪽** —
런타임 계약을 공유하는 상대 저장소가 실재하고, 코드가 이미 쌓여 있으며,
**에이전트 훅과 명령 가드가 이미 설치돼 있다.**

1회차에서 "다음 적용에서 볼 것" 으로 남긴 셋을 여기서 처음 잰다 —
짝 저장소(골격 4) · 기존 코드가 많은 곳의 `--audit`(골격 2) · **부트스트랩 소요 시간**.

---

## 1. 결과 요약

| | |
| - | - |
| **부트스트랩 소요** | **7분** (①복사 15:52 → ⑤훅 연결·발동 확인 15:59) · v0 기준 1 = 30분 |
| 검증 사다리 | ①설정 ②프로토콜 ③발동 — **전부 그린**. ③은 **위임 없이 이 세션 안에서** 닫혔다 |

| 발견 | 하네스 결함 0 · **문서 구멍 2** · 절차 요구사항 승격 3 · 긍정 발견 2 |

전체 소요는 11분이었다(부트스트랩 7분 + 골격 2·4 실측 4분).

## 2. 발견

### 🔴 F13 — ⭐⭐ 이미 가드가 깔린 프로젝트에서는 프로브 3기준이 서로 충돌한다

이 대상에는 명령 가드가 이미 있었다. 그런데 내가 첫날 규칙으로 고른 **네 개가 전부**
그 가드에 이미 덮여 있었다 — 이력 재작성 · 볼륨 삭제 · 빌드 데몬 일괄 종료 · 공유 DB 쓰기.
1회차에서 세운 프로브 선정 3기준(①무해 ②대상 가드에만 걸림 ③서명으로 주체 확인)을 만족하는
**실규칙이 하나도 없다.**

우연이 아니라 구조다. 남의 가드가 안 덮는 위험 명령이란 곧 **아무도 안 막던 진짜 위험한 것**이고,
그건 정의상 무해하지 않다. **성숙한 프로젝트일수록 ①과 ②는 교집합이 빈다.**

→ **검증 전용 프로브 규칙**을 설정에 명시적으로 두는 것으로 해결했다. 아무 일도 하지 않는 표식
문자열 하나를 deny 에 넣고, 그 표식을 출력하는 무해한 명령으로 발동을 쟀다.
막을 것이 없는 규칙이라 위험을 다루지 않으면서, 서명이 뜨면 주체가 확정된다.

⭐ 절차 요구사항으로 승격: **프로브 규칙은 실규칙에서 고르지 말고 검증용으로 하나 심는다.**
실규칙에서 고르려 하면 위 충돌에 걸려, 결국 위험한 프로브를 쓰거나 발동 검증을 건너뛰게 된다.
(골격 1 에 프로브 슬롯을 정식으로 두고 `--status` 의 규칙 수와 분리해 세는 편이 낫다 — v1 과제.)

### 🟢 F14 — ⭐ 적용 대상 안에서 부트스트랩하면 ③이 위임 없이 닫힌다

1회차의 ③은 **사람 손이 필요했다.** 대상이 작업 중이던 곳과 다른 폴더였고,
헤드리스 대행은 거짓 음성(F9), 직접 실행도 훅을 안 탄다(F11) — 즉 **대상 폴더에서 대화형 세션을
새로 여는 것** 외에 방법이 없었다.

이번에는 대상이 **지금 작업 중인 프로젝트 자신**이라, 훅을 연결한 직후 도구 호출로 프로브를 실행해
그 자리에서 판정을 받았다. 같은 절차인데 사람 개입이 0이다.

→ 부트스트랩에 배치 권고를 넣는다: **적용 대상에서 대화형 세션을 열고 그 안에서 절차를 밟는다.**
바깥에서 남의 프로젝트에 설치하면 ⑤의 마지막 한 칸(③발동)이 반드시 남는다.

### 🟢 F15 — 훅 설정 변경이 세션 재시작 없이 반영됐다 (실측)

훅 설정을 고친 직후, **같은 세션에서** 프로브가 차단됐다. 설정 변경 → 재시작 → 재검증의
왕복을 절차에 넣지 않아도 된다. (도구 버전에 따라 달라질 수 있는 성질이라 사실로만 남긴다.)

### 🔴 F16 — ⭐ 선실측이 과대계상된다 — 탐색 규칙이 프로젝트 관습과 어긋날 때

`--audit` 첫 출력은 **테스트 없음 32건**(deny 10)이었다. 그런데 그중 몇 건은 **테스트가 있었다.**
이 프로젝트는 하위 디렉토리의 테스트를 **한 단계 위의 테스트 디렉토리 한 곳에 모으는데**,
기본 탐색 규칙은 대상 파일의 형제 디렉토리만 본다. 상위를 보게 고치자 **32 → 29**(deny 10 → 7).

위험의 방향이 거짓 활성(F1)과 정반대다. 거짓 활성은 안심시켜서 위험하고, 이건 **겁을 줘서**
위험하다 — 숫자가 실제보다 크게 나오면 "이 프로젝트엔 못 켜겠다" 는 결론이 나고,
도입 절차의 핵심인 선실측이 도입을 포기시키는 근거가 된다.

→ 절차 요구사항으로 승격: **`--audit` 숫자를 읽기 전에 표본 몇 건을 손으로 대조한다.**
한 건이라도 "있는데 없다고 세어진" 것이 나오면 숫자가 아니라 `testLookup` 을 먼저 고친다.
⭐ 이 대조를 건너뛰면, 켜기 전에 재라는 규율이 있어도 **잘못 잰 숫자로 결정하게 된다.**

### 🟡 F17 — 짝끼리만 비교하면 "둘 다 낡은" 경우를 못 본다

두 저장소의 자산 4쌍(에이전트·훅·스킬·커맨드)을 걸고 처음 돌렸을 때 **차이 0** 이었다.
그런데 이 자산들에는 사용자 전역에 **원본**이 있고, 그 원본과 어긋나는 것은 짝끼리의 비교로는
영원히 보이지 않는다 — 사본 둘이 사이좋게 같이 낡으면 감시는 계속 조용하다.

→ 원본과의 쌍을 미러에 추가했다. 골격 4 의 한계 서술("선언되지 않은 자산은 아무도 감시하지 않는다")
과 같은 뿌리인데, 이번 건은 **선언은 했지만 축을 하나만 선언한** 경우다.
문서에 축 개념을 추가한다: **사본↔사본만이 아니라 사본↔원본도 쌍이다.**

### 🟢 F18 — 골격 4 의 전 경로가 실증됐다 (검출 → 승인 → 침묵)

하네스를 한쪽 저장소에만 먼저 깔았으므로 훅 설정 파일이 실제로 비대칭이 됐다.
그 자산을 미러에 넣자 **내용 차이 1건을 양쪽 수정 시각과 함께 보고**했고, 사유를 적어
승인된 차이로 등록하자 **조용해졌다**(새 차이 0 · 승인된 차이 1). 지금까지 코드로만 있던 경로다.

⭐ 승인 사유에 **해제 조건**을 함께 적었다("짝 저장소에도 적용하면 이 항목을 지운다").
조건 없는 승인은 영구 면제가 되어 감시 구멍으로 굳는다.

### 🟡 F19 — 하네스 도입은 빈 자리에만 한다 (판단 기록)

골격 2 는 `--audit` 까지만 하고 **켜지 않기로 판정**했다. 이 프로젝트에는 같은 일을 하는
가드가 이미 파일 편집 훅에 걸려 있어, 켜면 같은 판정을 두 번 하게 된다.
골격 1 도 사실상 같은 상황이지만(F13), 그쪽은 발동 검증이라는 목적이 있어 유지했다.

→ **하네스는 없는 것을 채우는 물건이지 있는 것을 대체하는 물건이 아니다.**
이미 있는 가드를 하네스 가드로 갈아끼우는 것은 이식이 아니라 교체이고, 그건 별도 결정이다.
설치 시 **기존 게이트 목록을 먼저 훑어 겹침을 확인하는 단계**를 부트스트랩에 넣는다.

## 3. 패널 조건부 2건은 어떻게 됐나

| 항목 | 상태 |
| - | - |
| 3-전문가(인계 체크리스트를 기계가 검증 못 함) | **재판정 불가** — 여전히 1인이라 역할 인계가 일어나지 않았다 |
| 7-전문가(배포 채널 1개 가정) | **조건이 처음 생겼다** — 하네스 사본이 두 곳이 됐다(아래) |

⭐ 이번 적용으로 **하네스 자신이 골격 4 의 대상이 됐다.** 복사해 넣는 설치 모델이라
두 프로젝트에 같은 골격 파일 사본이 생겼고, 원본은 하네스 저장소에 있다. 사본↔원본 축(F17)이
바로 이 구조다. 골격 7(배포 기계)이 다룰 문제가 실물로 나타났다 — 다만 아직 사본이 낡지는 않았다.

## 5. 다음 적용에서 볼 것

- **하네스 사본이 낡는 경로** — 원본을 고친 뒤 두 사본이 어떻게 갈라지는지. 골격 7 의 첫 조건이다.
- **짝 저장소 쪽에도 설치** — 계약 커플링(한쪽만 고치면 런타임에 깨지는 축)은 아직 전혀 안 잰다.
  지금 미러는 에이전트 설정 자산일 뿐 **코드 계약이 아니다.**
- **역할이 둘 이상인 프로젝트** — 패널 조건부 3-전문가는 그 전에는 못 닫는다.
