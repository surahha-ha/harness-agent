# 검토 판정 기록 — "실행형 구조 리디자인" 제안

외부에서 작성된 리디자인 제안 문서(2026-08-14 접수)를 기존 문서 전부와 대조해 판정한 기록.
제안 원문은 보존하지 않는다 — 주장 요지는 아래 표에 담겨 있고, 규약의 SSOT 는 언제나
[01-skeletons.md](01-skeletons.md) 다. 같은 규약을 두 문서에 살게 두지 않는다(골격 5 원칙 1).

> 이 기록을 남기는 이유: **기각에도 근거가 있어야 같은 제안이 반복되지 않는다.**
> 채택/기각의 기준 자체가 하네스 규율의 실전 사례라서 판정 과정을 보존한다.

## 사실 정정

제안 문서는 "현재 하네스는 이미 드리프트 감시·품질 사이클 등을 보완해 놓았다" 고 서술했으나
**사실이 아니다** — 구현된 골격은 1(위험 명령 가드)뿐이고 나머지는 명세만 있다.
상태의 SSOT 는 [01-skeletons.md](01-skeletons.md) 상단 표다("명세 완료 ≠ 구현 완료").

## 판정에서 얻은 교훈

- **"실행형으로 전환해야 한다" 는 문제의식은 맞았다. 처방이 틀렸다.** 실행형 전환의 실체는
  훅 실연결(자동 실행되는 게이트)이지 문서·체크리스트 추가가 아니다. 문서를 늘리는 처방은
  오히려 "설계형" 을 강화한다.
- **해소된 발견을 다시 제안받는 경로가 실재한다.** 이 제안의 기각 3건은 전부 패널 v0 와 필드
  리포트가 이미 잡아서 고친 것들이다. 발견 → 수정의 이력이 문서에 남아 있어도, 검토자가
  "수정함" 표기를 건너뛰면 같은 지적이 미해결로 되살아난다. 판정 기록을 남기는 이유가 이것이다.

## 이 판정이 바꾸지 않은 것

우선순위는 그대로다 — ①훅 실연결 재측정 ②v0 완료 기준 확정 ③짝 저장소 프로젝트 2회차 적용.
